### **11-5.4 – PostgreSQL Persistence Sink (Optional)**

This one is optional but nice.

**Minimal model**

```python
class EpistemicEventModel(Base):
    __tablename__ = "epistemic_events"

    id = Column(UUID, primary_key=True)
    event_type = Column(String)
    knowledge_unit_id = Column(UUID, index=True)
    timestamp = Column(DateTime(timezone=True), index=True)
    payload = Column(JSONB)   # full to_json_schema()
```

**Sink**

```python
class PostgresSink(EpistemicAuditSink):
    def __init__(self, session_factory):
        self._session_factory = session_factory

    def handle_event(self, event: EpistemicEvent) -> None:
        session = self._session_factory()
        try:
            model = EpistemicEventModel(
                id=event.event_id,
                event_type=event.event_type.value,
                knowledge_unit_id=event.knowledge_unit_id,
                timestamp=event.timestamp,
                payload=event.to_json_schema(),
            )
            session.add(model)
            session.commit()
        except Exception:
            session.rollback()
            # log warning, never raise to caller
        finally:
            session.close()
```

**ACs**

* AC1: On Postgres down, ingestion still works; only audit persistence is degraded (and logged).
* AC2: `get_forensic_timeline` can optionally be backed by DB instead of RAM.
* AC3: Simple migration path: one alembic migration, no changes to existing models.

## 1. 11-5.1 – Dual-Persona LLM Integration

Focus less on the plumbing and more on **behavioural invariants**:

1. **Verdict alphabet is closed and small**
   Make sure `_parse_llm_verdict()` only admits something like:

   * `{"verdict": "approve" | "deny" | "pending"}`
   * or an internal enum → mapped to `True/False/PENDING`
     Anything else → **PENDING + freeze** + audit event.

2. **Freeze semantics are correct**

   * Case A: `A=approve & D=approve` → **promotion allowed**
   * Case B: `A≠D` → **freeze**
   * Case C: LLM error / timeout / nonsense → **freeze**
     From the log: he added `any_pending → freeze`, which is what you want.

3. **Graceful degradation path**

   * When no provider / provider disabled → pure heuristic path
   * When provider flaky → doesn’t crash ingestion, just marks:

     * verdict = PENDING
     * freeze event + C-IDS hook

4. **Audit safety**
   Check that **only IDs / tiers / reasons** are logged, not full chunks or raw LLM prompts. Especially in:

   * contradiction events
   * persona disagreement logs
   * usage violation logs

If those invariants hold, 11-5.1 is safe to ship.

## 2. 11-5.2 – Audit Sink Architecture

Here you mainly validate that **EpistemicAuditLog stayed semantic** and sinks are thin I/O:

1. **Core class is still in charge of semantics**

   * Tier transitions, trust events, contradiction, freeze, usage violations
   * Log methods still build the canonical `EpistemicEvent*` objects
   * Sinks receive *events*, not arbitrary dicts.

2. **Sink fan-out and isolation**

   * Multiple sinks allowed (in-memory + stdout + Postgres).
   * A failure in one sink **must not**:

     * break the others
     * throw back into the reasoning path
       Pattern you want: best-effort I/O, epistemic logic never blocks on storage.

3. **Backward compatibility**

   * Old tests around `EpistemicAuditLog` without sinks must still pass.
   * Default behaviour == previous in-memory semantics.

4. **Protocol surface is minimal**
   `EpistemicAuditSink` should have something like:

   * `write(event: EpistemicEvent) -> None`
     Maybe batch later, but single-event interface is fine for now.

If these pass, your audit layer is objectively better than 99% of production systems.

## 3. 11-5.3 – Stdout JSON Sink

This is your **bridge to Graylog/ELK/Loki**.

Check:

1. **One event = one JSON line**

   * No multi-line dumping
   * No pretty-print
     → Sane for ingestion pipelines.

2. **Redaction discipline**

   * No full `text` or chunk content
   * Only:

     * IDs
     * tiers
     * event type
     * reason labels
     * trust numbers
     * timestamps
       If you need context, put a **short code** that you can later join with DB, not the human text itself.

3. **Structlog integration** (if he used it)

   * Logger name / component field present
   * Correlation IDs or request IDs optional but nice
   * Level = INFO for normal events, WARN/ERROR only on sink failure, not on epistemic “normal contradictions”.

This sink is purely observability, so you just ensure it doesn’t leak or spam.

## 4. 11-5.4 – Postgres Sink

This is the only one that can blow up if badly done, so quick sanity pass:

1. **Model is aligned with event schema**

   * `event_type`, `knowledge_unit_id`, `timestamp`, `reason`
   * JSONB for `metadata` is ideal
   * Optional fields for tiers, trust deltas, etc.

2. **Write path is defensive**

   * Transaction per event is fine for now
   * On DB error:

     * log at sink level
     * do **not** propagate to reasoning path
       Later you can batch or async this away if needed.

3. **No PII / raw content**
   Same story: IDs + structured data only.

4. **Migration strategy**

   * Alembic migration present
   * Feature can be toggled off if DB not ready.
